# Requirements Document

## Introduction

This feature implements the `sendMessage` Socket.IO event for the real-time chat application. When a client emits `sendMessage`, the server validates the payload, confirms the socket is a member of the target room, constructs a canonical message object, and broadcasts a `newMessage` event to every socket in that room (including the sender). No message persistence is introduced in this commit — the feature is a pure in-memory broadcast layer built on top of the room membership established by the `room-management` feature.

## Glossary

- **Socket**: A single persistent WebSocket connection between a client and the Socket.IO server, identified by `socket.id`.
- **Room**: A named channel identified by a `roomId` string. Sockets join rooms via the `room-management` feature before sending messages.
- **Message_Handler**: The server-side module (`server/src/socket/messageHandler.js`) responsible for processing `sendMessage` events, validating payloads, and broadcasting `newMessage` events.
- **Sender**: The socket that emits the `sendMessage` event, identified by `socket.id`.
- **Message_Payload**: The canonical object broadcast to all room members, containing `messageId`, `senderId`, `roomId`, `message`, and `timestamp`.
- **Broadcast**: A Socket.IO emission sent to all sockets currently joined to a specific room, including the sender, via `io.to(roomId).emit`.

## Requirements

### Requirement 1: Send Message Event

**User Story:** As a connected client, I want to send a message to a room I have joined, so that all members of that room receive it in real time.

#### Acceptance Criteria

1. WHEN a socket emits a `sendMessage` event with a `{ roomId, message }` payload, THE Message_Handler SHALL validate the payload before any broadcast.
2. WHEN the payload is valid and the socket is a member of the target room, THE Message_Handler SHALL broadcast a `newMessage` event to all sockets in that room via `io.to(roomId).emit`.
3. THE `newMessage` broadcast SHALL include all sockets in the room, including the Sender.
4. WHEN a `sendMessage` event is processed successfully, THE Message_Handler SHALL NOT persist the message to Redis or any other storage.

### Requirement 2: Message Payload Validation

**User Story:** As a system operator, I want the server to reject malformed or oversized messages before broadcasting, so that clients always receive well-formed message objects.

#### Acceptance Criteria

1. IF a `sendMessage` event is received with a missing or non-string `roomId`, THEN THE Message_Handler SHALL emit an `error` event to the Sender with a descriptive message and SHALL NOT broadcast to any room.
2. IF a `sendMessage` event is received with an empty `roomId` (zero-length after trim), THEN THE Message_Handler SHALL emit an `error` event to the Sender and SHALL NOT broadcast to any room.
3. IF a `sendMessage` event is received with a missing or non-string `message`, THEN THE Message_Handler SHALL emit an `error` event to the Sender with a descriptive message and SHALL NOT broadcast to any room.
4. IF a `sendMessage` event is received with a `message` that is empty or composed entirely of whitespace, THEN THE Message_Handler SHALL emit an `error` event to the Sender and SHALL NOT broadcast to any room.
5. IF a `sendMessage` event is received with a `message` whose trimmed length exceeds 2000 characters, THEN THE Message_Handler SHALL emit an `error` event to the Sender and SHALL NOT broadcast to any room.

### Requirement 3: Room Membership Check

**User Story:** As a system operator, I want the server to verify that a socket is actually in a room before broadcasting its message, so that sockets cannot send messages to rooms they have not joined.

#### Acceptance Criteria

1. WHEN a `sendMessage` event passes payload validation, THE Message_Handler SHALL check whether the socket is a member of the target room using `socket.rooms.has(roomId)`.
2. IF the socket is not a member of the target room, THEN THE Message_Handler SHALL emit an `error` event to the Sender with a descriptive message and SHALL NOT broadcast to any room.

### Requirement 4: Broadcast Payload Schema

**User Story:** As a client developer, I want every `newMessage` event to carry a consistent, complete payload, so that I can reliably render messages without additional lookups.

#### Acceptance Criteria

1. THE Message_Payload broadcast in every `newMessage` event SHALL contain a `messageId` field that is a UUID v4 string generated by the server at broadcast time.
2. THE Message_Payload SHALL contain a `senderId` field set to the `socket.id` of the Sender.
3. THE Message_Payload SHALL contain a `roomId` field set to the `roomId` from the validated `sendMessage` payload.
4. THE Message_Payload SHALL contain a `message` field set to the trimmed text from the `sendMessage` payload.
5. THE Message_Payload SHALL contain a `timestamp` field set to `Date.now()` (Unix milliseconds) at the moment of broadcast.

### Requirement 5: Error Handling

**User Story:** As a client developer, I want to receive a structured error event when my `sendMessage` call is rejected, so that I can display meaningful feedback to the user.

#### Acceptance Criteria

1. WHEN THE Message_Handler emits an `error` event to the Sender, the error payload SHALL contain a `message` field with a human-readable description of the failure reason.
2. WHILE the Socket.IO server is running, THE Message_Handler SHALL handle all validation and membership failures without throwing unhandled exceptions that could crash the server process.
3. IF an unexpected error occurs during broadcast (e.g., an internal Socket.IO error), THEN THE Message_Handler SHALL log the error with `roomId` and `socket.id` context and SHALL emit an `error` event to the Sender.
